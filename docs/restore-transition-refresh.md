# 恢复前刷新单窗口 DWM 过渡标志（本地 V13）

此前 `DisableTransitions` 把 HWND 放入缓存后就跳过后续调用，同时未检查 `DwmSetWindowAttribute` 是否成功。这会把调用失败记成成功，也无法应对应用在扫描和恢复之间自行改变 DWM 过渡属性的情况。

本次仅在合成器预览落地、提交真实窗口恢复之前，重新设置该窗口的 `DWMWA_TRANSITIONS_FORCEDISABLED`。普通扫描仍复用缓存；失败调用不进入缓存，可在下次重试；成功刷新的窗口沿用同一条退出清理记录。未修改系统动画开关、窗口样式、HDR 捕获和快照算法。[微软文档](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/ne-dwmapi-dwmwindowattribute)说明该属性控制目标窗口的 DWM 过渡。

六组确定性回归：96 项托盘/窗口、16 项网站图标、82 项状态栏、40 项动画、23 项输入法、17 项任务栏，共 **274 项通过**。动画新增三项覆盖调用被拒绝后不缓存、后续成功重试，以及模拟目标应用清除属性后，在真正恢复前刷新属性且不重复登记清理项。

候选 EXE 为 455,680 字节，相比 23:24:45 的快版 455,168 字节增加 512 字节。DLL 导入列表相同，`.bss` 大小相同。不把这些检查等同于所有真实应用的动画录像验证或整进程资源测量。

实机验证：用户在候选版中从 Dock 恢复 Firefox 后，明确确认“第二个动画已消失”。资源管理器普通窗口首轮顶部记录也未看到重复动画。上述结果支持本机修复有效，不等同于已经定位 Firefox 内部哪次操作改变了属性，也不覆盖所有应用或权限组合。独立恢复驱动没有进入完整 Dock 主循环，其首轮耗时不能与此前 375 ms 的实际 Dock 恢复数据比较；本轮不宣称新的整段恢复耗时。

原快版 EXE 已保留为 `MiniDock.exe.fast.bak`，三个源码 `.fast.bak` 和原 v12 试用包保留。V13 已更新正式源码目录中的 EXE 并另打包试用目录和 ZIP，ZIP 完整性与其中 EXE 的一致性检查通过。未提交、推送或发布到 GitHub。

切换时另检查了真实退出和重启：退出后主任务栏重新可见，任务栏状态值恢复前后均为 0；系统的窗口最小化/恢复动画和客户区动画持续开启。重新启动正式源码目录的 V13 后，任务栏按原配置隐藏。记录位于工作区 `_lead_probe/runs/v13-finalization.json`。

运行权限补充：初次切换时 Dock 被普通权限启动，随后用户反馈 OrCAD 和微信无法收回。只读令牌检查显示 Capture 为高完整性（0x3000），微信的多个进程同为高完整性，而当时 Dock 为中完整性（0x2000）。已通过 Windows 管理员确认重新启动同一份 V13；主进程和守护进程均验证为 0x3000，EXE 未改。控制管理员应用时应保留这一启动权限，不能把普通权限下的窗口控制失败误判为 HDR 修复回归。
